## 0. Read this first

### 0.1 What nvEnvy is

A markdown note-taking app for macOS 14+ and iOS 17+. Two layers:

- **`NvEnvyCore/`** — a SwiftPM package (`Sources/NvEnvyCore/`) holding the data
  model (`Note`), file I/O (`FileStorageService`, `NoteStore`), search
  (`SearchEngine`, `SearchActor`), frontmatter parsing (`FrontmatterParser`),
  markdown rendering, and the crash-recovery WAL. Shared by both platforms.
- **`nvEnvy/`** — the app targets. `nvEnvy/nvEnvy/` is macOS (SwiftUI + AppKit
  `NSTextView`); `nvEnvy/nvEnvyiOS/` is iOS (SwiftUI + UIKit `UITextView`).
  The Xcode project is generated by XcodeGen from `nvEnvy/project.yml`.

Notes are plain `.md` files on disk with YAML frontmatter. That is the product's
entire value proposition — see §2.1.

### 0.2 Build and test

```bash
cd NvEnvyCore && swift test          # ~168 unit tests; must stay green
cd nvEnvy && xcodegen generate       # regenerate after editing project.yml
xcodebuild -project nvEnvy/nvEnvy.xcodeproj -scheme nvEnvy build
```

Existing benchmarks live in
`NvEnvyCore/Tests/NvEnvyCoreTests/PerformanceTests.swift`:
`testSearchPerformance5000Notes`, `testFileIOBenchmark1000Notes`,
`testWALBenchmark1000Records`, `testLargeNoteHandling`,
`testMemoryBaseline10000Notes`.

## 2. Do not do this

### 2.1 Architectural rejections (unchanged, still correct)

1. **Do not replace markdown files with SQLite / Core Data / SwiftData.**
   Interoperability via plain `.md` + YAML on disk is the core user contract.
   Migrating breaks Obsidian, Marked 2, VS Code, and Finder sync. The
   actor-backed in-memory `NoteStore` is adequate well past any realistic vault
   size.

2. **Do not replace `@Observable` with `ObservableObject`.** Observation gives
   property-level dependency tracking; `ObservableObject` invalidates entire
   views on any published mutation. That is strictly worse. (Note: property-level
   tracking is also *why* P4 is subtle — see §3.5.)

3. **Do not convert `Note` from a class to a struct.** `NoteStore`,
   `NotesViewModel`, `AppState`, and the `NSTextView`/`UITextView` coordinators
   all depend on reference identity. Value semantics would mean copy-on-write of
   large bodies plus desynchronization across isolation boundaries.

4. **Do not pre-render `WKWebView` for unselected notes.** Each WebContent
   process costs tens of MB; speculative rendering invites jetsam on iOS.

5. **Do not hand-roll a POSIX thread pool in `FileStorageService`.**
   `withTaskGroup` already saturates the performance cores.

### 2.2 Optimizations rejected in this revision

These appeared in the previous draft. Each was checked against the source and
found unsound, unmeasurable, or not worth the risk.

6. **Do not make `Note.cachedLowercaseBody` lazily populated.**
   `Note` is `@Observable ... @unchecked Sendable` and the *same instances* are
   held by `NotesViewModel` on `@MainActor` and passed by reference into
   `SearchActor.filter`. A lazily-populated `var` means the search actor
   **writes** to a note while the main actor may be writing `body` on a
   keystroke — an unsynchronized data race. The actor isolates the engine's
   state, not the `Note` objects handed to it. The current eager-init design is
   race-free precisely *because* the caches are written only in `init` and
   `invalidateSearchCache()`.
   Laziness also just relocates the cost: the first keystroke in the search
   field would lowercase the whole corpus on the *interactive* path instead of
   during load.
   *If* memory becomes a demonstrated problem (measure
   `testMemoryBaseline10000Notes` first), the correct fix is to **delete**
   `cachedLowercaseBody` entirely and search the original body with
   `range(of:options:.caseInsensitive)` — removing the memory *and* the race.
   That is a separate, larger proposal requiring its own benchmarks.

7. **Do not add `-cross-module-optimization`, `LLVM_LTO`, or explicit
   `SWIFT_COMPILATION_MODE` to `project.yml`.**
   - CMO is a property of the module *being compiled*, so putting the flag in
     the app target's `OTHER_SWIFT_FLAGS` does nothing for `NvEnvyCore`. It
     would have to go in `NvEnvyCore/Package.swift` as an `unsafeFlags`
     swiftSetting — which SwiftPM **refuses** for a package consumed as a
     dependency. This is why it is not already there.
   - Release configurations already get `-O` and whole-module compilation by
     default; "not written in `project.yml`" is not the same as "disabled."
   - `DEAD_CODE_STRIPPING` already defaults to `YES`.
   The only genuinely available mechanism here is `@inlinable` on specific hot
   functions, and there is currently no profile identifying any. Revisit after
   P0.

8. **Do not rewrite `WordCountOverlay.computeStats`.**
   It is already behind a 300 ms debounce (`nvEnvy/nvEnvy/EditorView.swift:46-53`),
   so it is invisible to the user. The proposed UTF-8 scan also retained
   `text.count` — the O(n) grapheme-breaking call that dominates the function —
   and would have narrowed word splitting from Unicode `isWhitespace` to four
   ASCII bytes, silently changing counts for text containing non-breaking or
   ideographic spaces.

9. **Do not replace `localizedCaseInsensitiveCompare` with `<` on
   `cachedLowercaseTitle` in `rebuildSortedNotes`.**
   Byte-order comparison sorts `é` after `z` and breaks numeric ordering
   (`note10` before `note2`). The sidebar sort order is a primary interface
   element; this is a visible regression, not the "minor" risk previously
   claimed. If title sorting shows up in a P0 trace, the acceptable fix is a
   precomputed sort key or
   `compare(options: [.caseInsensitive, .numeric])` — and it needs its own
   benchmark, since `rebuildSortedNotes` is not on the typing path.

### 3.1 [P0] Add `os_signpost` instrumentation

**Do this first. Everything else in this document is guesswork until it lands.**

**Files:**
- `NvEnvyCore/Sources/NvEnvyCore/` — new file `PerformanceTelemetry.swift`
- `NvEnvyCore/Sources/NvEnvyCore/FileStorageService.swift` — `readAllNotes()`
- `NvEnvyCore/Sources/NvEnvyCore/SearchEngine.swift` — `SearchActor.filter`
- `NvEnvyCore/Sources/NvEnvyCore/NoteStore.swift` — `reconcilePaths`
- `NvEnvyCore/Sources/NvEnvyCore/NotesViewModel.swift` — `performSearch()`,
  `rebuildSortedNotes()`

**Problem:** There is no structured telemetry for launch, parse, reconciliation,
or search. Every performance claim about this codebase to date has been
inferred from reading code rather than measured.

**Fix:** Add a shared signposter:

```swift
import OSLog

public enum PerformanceTelemetry {
    public static let logger = Logger(subsystem: "com.nvenvy.app", category: "Performance")
    public static let signposter = OSSignposter(logger: logger)
}
```

Wrap each site above in
`signposter.beginInterval(...)` / `signposter.endInterval(...)`. Use
`withIntervalSignpost` where the scope is a single expression. For
`readAllNotes()`, emit the note count as signpost metadata so per-note cost is
derivable.

**Invariants:**
- Signpost overhead when not recording is negligible, but do **not** place a
  signpost inside the per-note loop of `readAllNotes` or the per-note loop of
  `SearchEngine.filter` — instrument the enclosing call only. Per-iteration
  signposts in a 10,000-iteration loop are themselves a measurable cost.

**Required tests:** None (no behavior change). Confirm `swift test` stays green.

**Verification:**
1. Instruments → *Points of Interest* / *os_signpost* template.
2. Cold-launch a vault of ~5,000 notes and record: total `readAllNotes`
   duration, and its share of time-to-first-frame.
3. Type a 6-character query and record per-keystroke `SearchActor.filter`
   duration.
4. **Write these numbers into the PR.** They become the baseline for P1–P8 and
   should be used to re-order the remaining items.

### 3.2 [P1] Reuse the existing static `isoFormatter`

**File:** `NvEnvyCore/Sources/NvEnvyCore/FrontmatterParser.swift`

**Problem:** A correctly-configured static formatter already exists at line 137
and is used by the parse path at line 157 — but the *serialize* path at line 220
constructs a fresh one on every write:

```swift
// FrontmatterParser.swift:220 (current)
    private static func formatDate(_ date: Date) -> String {
        let iso = ISO8601DateFormatter()
        iso.formatOptions = [.withInternetDateTime]
        return iso.string(from: date)
    }
```

`ISO8601DateFormatter` initialization pulls in ICU calendar setup. This runs on
every note write, i.e. on every autosave.

**Fix:**

```swift
    private static func formatDate(_ date: Date) -> String {
        isoFormatter.string(from: date)
    }
```

**Invariants:**
- **Read `isoFormatter`'s definition at line 137 before editing.** This fix is
  only valid if its `formatOptions` are exactly `[.withInternetDateTime]`. If
  they differ (e.g. include `.withFractionalSeconds`), the serialized output
  format would change and rewrite every note's frontmatter on next save. In that
  case, add a *second* static formatter configured for
  `[.withInternetDateTime]` rather than reusing the parse-side one.
- `ISO8601DateFormatter` is thread-safe for formatting; a shared static is
  correct here.

**Required tests:** `FrontmatterParserTests.testSerializeWithDates` already
covers the output format. Confirm it passes unchanged.

### 3.3 [P2] Fix Unicode range bug in search highlighting

**This is a correctness fix that happens to also remove an allocation.**

**Files:**
- `nvEnvy/nvEnvy/EditorView.swift:443-444` — `Coordinator.highlightSearchTerms`
- `nvEnvy/nvEnvyiOS/Editor/EditorCoordinator.swift:333-334` —
  `EditorCoordinator.highlightSearchTerms(in:)`

Note the two files read the query from different objects — macOS uses
`appState.searchQuery`, iOS uses `notesVM.searchQuery`. Preserve each.

**Problem:** Both coordinators lowercase the entire document, compute `NSRange`s
against the lowercased copy, and then apply those ranges to the **original**
text storage:

```swift
// EditorCoordinator.swift:333-334 (current; macOS equivalent at EditorView.swift:443-444)
        let query = notesVM.searchQuery.lowercased()
        let nsText = text.lowercased() as NSString
```

`lowercased()` is **not length-preserving in Unicode**. `İ` (U+0130) lowercases
to two scalars (`i` + U+0307); several other characters expand similarly. When
the note contains any such character before a match, every subsequent computed
range is shifted, so highlights land on the wrong characters — and a range near
the end of the document can exceed the original string's length, which is a
crash, not just a cosmetic bug.

Separately, it allocates a full copy of the document on every search keystroke.

**Fix:** Search the original `NSString` with `.caseInsensitive`. iOS version:

```swift
    func highlightSearchTerms(in textView: UITextView) {
        let textStorage = textView.textStorage
        let text = (textView.text ?? "") as NSString
        let fullRange = NSRange(location: 0, length: text.length)

        textStorage.removeAttribute(.backgroundColor, range: fullRange)

        guard prefs.searchHighlight, !notesVM.searchQuery.isEmpty else { return }
        let query = notesVM.searchQuery

        var searchRange = fullRange
        while searchRange.location < text.length {
            let foundRange = text.range(of: query, options: .caseInsensitive, range: searchRange)
            guard foundRange.location != NSNotFound else { break }
            textStorage.addAttribute(.backgroundColor, value: Self.searchHighlightColor, range: foundRange)
            searchRange.location = foundRange.location + foundRange.length
            searchRange.length = text.length - searchRange.location
        }
    }
```

Apply the equivalent change to the macOS `Coordinator`, keeping its existing
attribute name, colour constant, and `appState.searchQuery` source.

**Invariants:**
- Guard against `foundRange.length == 0` if the query can ever be empty after
  the guard — advance `searchRange.location` by at least 1 to avoid an infinite
  loop. The `!searchQuery.isEmpty` guard covers this today; keep it.
- Do **not** add `.diacriticInsensitive`. That would change which text matches.
- `EditorView.swift:531` also calls `.lowercased()`, on a short substring for
  autocomplete. That is unrelated and correct — leave it alone.

**Required tests:**
- Add a unit test for the range arithmetic. Extract the match-range computation
  into a testable pure function taking `(text: NSString, query: String) ->
  [NSRange]` if it is not already separable.
- The test **must** include `İstanbul` (or another expanding-lowercase
  character) followed by a later match, and assert the returned range maps to
  the correct substring of the *original* text.
- **Run this test against the unmodified code first and confirm it fails.**
  That is the proof the bug is real.

### 3.4 [P3] Early-out in `FrontmatterParser.parse` for notes without frontmatter

**File:** `NvEnvyCore/Sources/NvEnvyCore/FrontmatterParser.swift:51`

**Problem:** `parse` splits the whole document into an array of line strings and
*only then* checks whether the note has frontmatter at all:

```swift
// FrontmatterParser.swift:51-56 (current)
    public static func parse(_ content: String) -> ParsedNote {
        let lines = content.components(separatedBy: "\n")

        guard !lines.isEmpty, lines[0].trimmingCharacters(in: .whitespaces) == "---" else {
            return ParsedNote(body: content)
        }
```

For a plain `.md` note with no frontmatter — the common case in an imported
nvALT vault — the entire body is split into an array of `String`s, and every one
of them is discarded on the next line. This runs for every file on cold launch.

**Fix — the early-out only:**

```swift
    public static func parse(_ content: String) -> ParsedNote {
        // Fast path: no frontmatter delimiter means nothing to parse. Avoids
        // splitting the whole document into lines just to discard them.
        guard content.hasPrefix("---") || content.hasPrefix(" ") || content.hasPrefix("\t") else {
            return ParsedNote(body: content)
        }

        let lines = content.components(separatedBy: "\n")
        // ... rest unchanged ...
```

The leading-whitespace cases are included because the existing guard applies
`trimmingCharacters(in: .whitespaces)` to line 0, so `  ---` currently parses as
frontmatter. Preserving that costs one extra prefix check and keeps behavior
identical.

**Invariants — read this before touching anything else in this function:**

A previous draft of this proposal replaced the whole function with substring
scanning. **Do not do that.** That rewrite was verified to introduce three
regressions:

1. It located the closing delimiter with `range(of: "\n---")`, which is not
   anchored to a full line. It therefore matches `----` (a common horizontal
   rule), `--- some text`, and a `---` inside a fenced code block. The current
   code requires `line.trimmingCharacters(in: .whitespaces) == "---"`. **This
   anchoring is load-bearing and must be preserved.**
2. It stripped all leading blank lines and indentation from the body via
   `drop(while:)`. Because notes round-trip to disk, that **rewrites the user's
   files** — unacceptable for an app whose value proposition is file fidelity.
3. It dropped support for leading whitespace before the opening `---`.

If you want to eliminate the line-array allocation for notes that *do* have
frontmatter, that is a legitimate follow-up — but it must scan for
newline-anchored `---` lines explicitly, and it needs the tests below to pass
first.

**Required tests** — add to
`NvEnvyCore/Tests/NvEnvyCoreTests/FrontmatterParserTests.swift`. The existing 12
tests do **not** cover these, which is how the rewrite above nearly shipped:

- `testBodyWithHorizontalRuleNotTreatedAsFrontmatter` — body containing a `---`
  or `----` horizontal rule on its own line, in a note with no frontmatter.
- `testFourDashDelimiterIsNotFrontmatterClose` — frontmatter closed by `----`
  should not be treated as a valid close.
- `testBodyLeadingBlankLinesPreserved` — frontmatter followed by two blank lines
  then text; assert the body retains both blank lines byte-for-byte.
- `testBodyLeadingIndentationPreserved` — body starting with an indented code
  block; assert indentation survives.
- `testLeadingWhitespaceBeforeOpeningDelimiter` — `"  ---\ntags: [a]\n---\nbody"`.
- `testFrontmatterInsideCodeFence` — a fenced code block containing `---`.

**Run all six against the unmodified code first.** They should all pass — they
are regression guards, not bug reports. If any fails on the current code, stop
and report it; that is a pre-existing bug and a separate change.

**Verification:** Compare `readAllNotes` signpost duration (from P0) on a vault
of notes with no frontmatter, before and after.

### 3.5 [P4] Stop `modifiedDate` churn from re-rendering list rows on every keystroke

**Read §3.5.1 before writing any code. The obvious fix does not work.**

**Files:**
- `NvEnvyCore/Sources/NvEnvyCore/NotesViewModel.swift:267-282` — `updateNoteBody`
- `NvEnvyCore/Sources/NvEnvyCore/Note.swift` — add a cached display string
- `nvEnvy/nvEnvy/NoteListView.swift:222-241` — `NoteRow`
- `nvEnvy/nvEnvy/NoteListView.swift:243-278` — `NotePreviewRow`
- `nvEnvy/nvEnvyiOS/UI/NoteListView.swift:157` — `noteRow(_:)`

**Problem:** Every keystroke in the editor sets `modifiedDate`:

```swift
// NotesViewModel.swift:267-282 (current)
    public func updateNoteBody(noteID: UUID, body: String) {
        guard let note = note(for: noteID) else { return }
        note.body = body
        note.modifiedDate = Date()
        pendingBodyUpdate = (noteID, body)

        // Debounce expensive work: search cache invalidation, WAL write.
        bodyUpdateTask?.cancel()
        bodyUpdateTask = Task { @MainActor [weak self] in
            try? await Task.sleep(for: .milliseconds(500))
            guard !Task.isCancelled, let self else { return }
            self.pendingBodyUpdate = nil
            note.invalidateSearchCache()
            await self.noteStore?.updateBody(noteID: noteID, body: body)
        }
    }
```

`modifiedDate` is an observed property of `@Observable Note`. Every list row
reads it and formats it:

```swift
// nvEnvy/nvEnvy/NoteListView.swift:227 (current)
        let modifiedString = note.modifiedDate.formatted(rowModifiedDateStyle)
```

```swift
// nvEnvy/nvEnvyiOS/UI/NoteListView.swift (current, inside noteRow)
            Text(note.modifiedDate, style: .date)
```

So each character typed invalidates the selected note's row and re-runs
`Date.FormatStyle` formatting, which is not cheap. `NotePreviewRow`'s
accessibility label additionally formats a `RelativeFormatStyle`.

#### 3.5.1 Why the obvious fixes do not work

A previous draft proposed making the iOS row `Equatable`. **That does not solve
this problem**, for two independent reasons:

- `Equatable` conformance on a `View` has no effect unless the view is wrapped
  in `EquatableView` or has `.equatable()` applied at the call site. The draft
  omitted this.
- More fundamentally, **`Equatable` cannot suppress Observation-driven
  invalidation.** If `body` reads `note.modifiedDate` and that property changes,
  SwiftUI's observation tracking invalidates *that view* directly. The parent's
  equality check is never consulted. `Equatable` only short-circuits
  *parent-driven* re-evaluation.

The same draft also proposed moving `note.modifiedDate = Date()` inside the
debounced task. **Do not do that either**: the task is cancelled on every
keystroke and on note switch, so if the user types and immediately switches
notes or quits, `modifiedDate` is never updated at all. The current eager
assignment exists for exactly that reason.

#### 3.5.2 The actual fix

Stop the row from *reading* `modifiedDate`. Add a pre-formatted, non-observed
display string to `Note`, refreshed on the same debounce that already refreshes
the search cache.

In `Note.swift`, alongside the existing `cachedFirstLine`:

```swift
    // List-render optimization: pre-formatted modified-date string. Not
    // observed, so per-keystroke `modifiedDate` churn does not invalidate rows.
    // Refreshed by `invalidateSearchCache()` (i.e. on the 500ms edit debounce).
    @ObservationIgnored public var cachedModifiedString: String
```

Initialize it in `init` and refresh it in `invalidateSearchCache()` using the
same `Date.FormatStyle` the rows use. Because the format style currently lives
in the macOS view file, move `rowModifiedDateStyle` / `rowRelativeDateStyle`
(`nvEnvy/nvEnvy/NoteListView.swift:219-220`) into `NvEnvyCore` so both platforms
and the model share one definition.

Then change the rows to read `note.cachedModifiedString` instead of
`note.modifiedDate`, on **all three** row types (macOS `NoteRow`, macOS
`NotePreviewRow`'s accessibility label, iOS `noteRow`).

**Invariants:**
- `modifiedDate` itself must **still be assigned eagerly** in `updateNoteBody`.
  Only the *displayed string* is debounced. Sorting by modified date, file
  writes, and FSEvents reconciliation all depend on the real value being
  current.
- The visible timestamp will therefore update ~500 ms after typing stops rather
  than per keystroke. This matches Notes, Bear, and Mail. Confirm this is
  acceptable before implementing — it is a deliberate, user-visible change.
- `cachedModifiedString` must be `@ObservationIgnored`, or the whole exercise is
  pointless.
- Rows sorted by `.modifiedDate` in `rebuildSortedNotes` still read the live
  property — that is correct and must not be switched to the cached string.
- **Locale/timezone changes:** the cached string will be stale if the user
  changes locale while the app runs. Observe
  `NSLocale.currentLocaleDidChangeNotification` (and, on iOS,
  `UIApplication.significantTimeChangeNotification`) and rebuild the cached
  strings, or accept the staleness and document it. Pick one and say which in
  the PR.

**Required tests:**
- `NoteCacheTests` — assert `cachedModifiedString` is populated at `init` and
  refreshed by `invalidateSearchCache()`.
- `NotesViewModelTests` — assert `modifiedDate` is updated **synchronously** by
  `updateNoteBody` (guards against the regression described in §3.5.1).

**Verification:** Instruments → *SwiftUI View Body*. Type continuously in a note
that is visible in the list. Assert row body invocations drop to at most one per
500 ms debounce tick, versus one per keystroke today. Record both counts.

### 3.6 [P5] Cache `custom.css`; precompute the conflict count

Two independent, low-risk removals of per-render work. Bundle them.

#### 3.6a `custom.css` re-read on every preview render

**File:** `nvEnvy/nvEnvy/PreviewWindow.swift:107-112`, called from
`renderNow()` at line 103.

```swift
// PreviewWindow.swift:107-112 (current)
    private func loadCustomCSS() -> String? {
        let appSupport = FileManager.default.urls(for: .applicationSupportDirectory, in: .userDomainMask).first
        guard let cssURL = appSupport?.appendingPathComponent("nvEnvy/custom.css"),
              let css = try? String(contentsOf: cssURL, encoding: .utf8) else { return nil }
        return css
    }
```

`renderNow()` runs on the preview's ~300 ms debounce while typing, so this does
synchronous main-thread disk I/O repeatedly during editing.

**Fix:** Cache the loaded string. Re-read on window appear and when the file's
modification date changes; a time-based check (e.g. at most once every 5 s) is
an acceptable simpler alternative.

**Invariants:** Users edit `custom.css` in an external editor and expect the
preview to pick it up. Do **not** cache for the process lifetime with no
invalidation. Whichever refresh trigger you pick, verify manually that editing
`custom.css` externally is reflected within a few seconds.

#### 3.6b `ConflictBanner` filters all notes on every render

**File:** `nvEnvy/nvEnvyiOS/UI/ConflictView.swift:37-39`
(note: **not** `NoteListView.swift`, as a previous draft claimed)

```swift
// ConflictView.swift:37-39 (current)
    private var conflictedNotes: [Note] {
        notesVM.allNotes.filter { $0.syncStatus == .conflict }
    }
```

`ConflictBanner` is installed as a `safeAreaInset` on `NoteListView`
(`nvEnvy/nvEnvyiOS/UI/NoteListView.swift:75`), so this full scan and array
allocation runs on every re-render of the note list.

**Fix:** Expose a precomputed `conflictedNotes` or `conflictedNoteCount` on
`NotesViewModel`, maintained where `syncStatus` is mutated. The banner reads
that.

**Invariants:** The sheet (`ConflictListView`) needs the actual notes, not just
a count — expose the array, or expose both. Ensure the precomputed value is
updated on every path that sets `syncStatus`, including FSEvents-driven

### 3.7 [P6] O(N) tier bucketing in `SearchEngine.filter`

**Do this for clarity, not for speed. See the expectations note below.**

**File:** `NvEnvyCore/Sources/NvEnvyCore/SearchEngine.swift:57-62`, and
`relevanceTier` at line 84.

**Problem:** `filter` sorts results by calling `relevanceTier` inside the
comparator:

```swift
// SearchEngine.swift:57-62 (current)
        // Sort by relevance: exact title match first, then title contains, then body/tag only
        let sorted = results.sorted { a, b in
            let tierA = relevanceTier(note: a, query: lowercaseQuery, tokens: tokens)
            let tierB = relevanceTier(note: b, query: lowercaseQuery, tokens: tokens)
            return tierA < tierB
        }
```

Each note's tier is recomputed roughly `2 log N` times instead of once.

**Expectations — read this.** The previous draft rated this P0 and predicted an
85–90% search speedup. That is wrong. `relevanceTier` only scans
`cachedLowercaseTitle`, which is short. The dominant cost of `filter` is the
`cachedLowercaseBody.contains(token)` scan over every note in the working set
(lines 45-55), which this change does **not** touch. Expect a small improvement.
It is worth doing because it is free and clearer, not because it is fast.

**Fix:** Compute each note's tier once, during the existing match loop, and
append into three arrays; concatenate at the end.

```swift
        var tier0Exact: [Note] = []
        var tier1Title: [Note] = []
        var tier2Other: [Note] = []

        for note in workingSet {
            var matchesAllTokens = true
            var allTokensInTitle = true
            for token in tokens {
                let inTitle = note.cachedLowercaseTitle.contains(token)
                if !inTitle { allTokensInTitle = false }
                if !inTitle
                    && !note.cachedLowercaseBody.contains(token)
                    && !note.cachedLowercaseTags.contains(token) {
                    matchesAllTokens = false
                    break
                }
            }
            guard matchesAllTokens else { continue }

            if note.cachedLowercaseTitle == lowercaseQuery {
                tier0Exact.append(note)
            } else if allTokensInTitle {
                tier1Title.append(note)
            } else {
                tier2Other.append(note)
            }
        }

        var sorted: [Note] = []
        sorted.reserveCapacity(tier0Exact.count + tier1Title.count + tier2Other.count)
        sorted.append(contentsOf: tier0Exact)
        sorted.append(contentsOf: tier1Title)
        sorted.append(contentsOf: tier2Other)
```

Note this reuses the `inTitle` result to derive `allTokensInTitle`, so the
title scan happens once per token rather than twice. Delete `relevanceTier`
once nothing calls it.

**Invariants:**
- **Ordering will change in some cases, and that is fine but must be
  acknowledged.** `Array.sorted` is not documented as stable, so the current
  intra-tier ordering is unspecified. Bucketing makes it stable in working-set
  order. This is a *better*-defined behavior, but do not claim "ordering
  preserved" in the commit message — say "intra-tier ordering is now stable."
- Careful with the `break`: when a token fails to match anywhere, the loop
  breaks and `allTokensInTitle` is left in a partial state. That is harmless
  because `matchesAllTokens` is false and the note is skipped — but if you
  restructure the loop, preserve that property.
- Preserve the incremental `workingSet` optimization (lines 33-41) exactly.

**Required tests:** `SearchEngineTests` already has 14 tests including
`testExactTitleMatch`, `testMultiTokenSearch`, `testPhraseSearch`,
`testIncrementalFiltering`. All must pass unchanged. Add one asserting that a
note matching only in the body ranks after a note matching in the title.

**Verification:** `testSearchPerformance5000Notes` and
`testPerformanceAt1KNotes` before/after. Report the real delta, whatever it is —
including if it is negligible.

### 3.8 [P7] Reuse `JSONEncoder` and `FileHandle` in the WAL

**File:** `NvEnvyCore/Sources/NvEnvyCore/CrashRecoveryService.swift:43, 56-62`

**Problem:** `appendRecord` constructs a `JSONEncoder` per call and opens, seeks,
writes, and closes a `FileHandle` per call:

```swift
// CrashRecoveryService.swift:43 (current)
        let jsonData = try JSONEncoder().encode(payload)
```

```swift
// CrashRecoveryService.swift:56-62 (current)
        if fileManager.fileExists(atPath: walURL.path) {
            let handle = try FileHandle(forWritingTo: walURL)
            handle.seekToEndOfFile()
            handle.write(record)
            handle.closeFile()
        } else {
            try record.write(to: walURL)
        }
```

**Fix:** Hoist a `private static let encoder = JSONEncoder()`. Hold the write
handle in a `private var activeHandle: FileHandle?` across appends, closing it
in `truncate()` and on deinit.

`CrashRecoveryService` is an `actor` (line 14), so the mutable handle is
correctly isolated.

**Invariants — this is the crash-recovery path; be conservative:**
- **`truncate()` (line 123-126) must close the handle before writing.** It
  currently does `try Data().write(to: walURL)`, which replaces the file. A
  stale open handle would then append at a bogus offset into an unlinked inode.
  Close first, set `activeHandle = nil`, then truncate.
- **Do not introduce any buffering.** `FileHandle.write` is an unbuffered
  `write(2)`, so durability is unchanged by keeping the handle open. Anything
  that batches writes in userspace defeats the purpose of a write-ahead log.
- `recoverPendingNotes()` (line 68) reads the WAL. Verify it still sees records
  written through the persistent handle — it should, since the data is in the
  page cache, but test it explicitly.
- Add `deinit` handling, or an explicit `close()` the app calls at termination.
  Note that actor `deinit` cannot call isolated methods; close the handle
  directly on the stored property.

**Required tests:** `CrashRecoveryServiceTests` — add a test that appends
records, calls `truncate()`, appends again, and asserts
`recoverPendingNotes()` returns only the post-truncate records. Confirm the
existing tests pass unchanged.

**Verification:** `testWALBenchmark1000Records` before/after.

### 3.9 [P8] WKWebView in-place update instead of full reload

**Lowest confidence item in this document. Do it last, or defer it.**

**File:** `nvEnvy/nvEnvy/PreviewWindow.swift` — `PreviewWebView.updateNSView`

**Problem:** `updateNSView` calls `loadHTMLString(html, baseURL: nil)` on every
render, tearing down the DOM, re-parsing CSS, resetting scroll position, and
producing a visible white flash while typing with the preview open.

**Fix, in two steps — land step 1 alone first:**

1. **Guard on unchanged HTML.** Store `lastLoadedHTML` on the coordinator and
   return early when the rendered HTML is identical. This alone eliminates a
   large share of reloads (the 300 ms debounce fires on cursor movement and
   no-op edits) and carries essentially no risk.

2. **Only if step 1 proves insufficient**, update the content element in place
   via `evaluateJavaScript`, falling back to `loadHTMLString` when the document
   is not yet initialized.

**Invariants for step 2:**
- The previous draft's approach — interpolating escaped HTML into a JS template
  literal and calling `document.write()` — is fragile. Escaping must handle
  backslashes, backticks, `${`, and unpaired surrogates, and any miss is either
  a broken render or a script-injection vector from note content.
  **Prefer passing the HTML as a JSON-encoded string argument** (via
  `JSONSerialization` or `JSONEncoder` on the string, which handles all escaping
  correctly) and assigning `element.innerHTML` — do not use `document.write()`,
  which requires reopening the document and discards the CSS you were trying to
  preserve.
- Preserving scroll position is the actual goal; verify it explicitly.
- Test with notes containing: fenced code blocks with backticks and `${`,
  inline `<script>` tags, emoji and astral-plane characters, and very large
  documents.

**Required tests:** Manual, documented in the PR. Type in a markdown note with
the preview docked side-by-side and confirm: no white flash, scroll position
held, and correct rendering for each adversarial case above.
